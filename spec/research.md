# 技术研究结论

## SQLite 任务队列

单机 MVP 使用 SQLite WAL。worker 在 `BEGIN IMMEDIATE` 事务内选择并抢占最早可用任务，运行期间每 30 秒更新任务心跳并周期扫描；超过两分钟没有心跳的 `running` 任务重新排队。这样既不需要 Redis，也避免 worker 异常退出后素材永久停留在“分析中”。

## 流式 multipart

Next.js Route Handler 使用 Busboy 读取 Web Stream 并直接写临时文件，检查接口对应的目标扩展名和上传大小后原子重命名并入队。客户端声明 MIME 仅保存作审计；内容签名、解码和格式转换由 worker 执行，避免大视频进入 JS 堆内存或长时间占用上传请求。

## 目标格式正规化策略

图片目标格式限定为浏览器和模型普遍可用的 JPEG、PNG、WebP；真实内容为其中另一种格式时，Sharp 在同目录生成临时产物，验证大小后原子替换。视频文件名限定为 `.mp4`；worker 只允许 FFmpeg 探测自包含的本地视频容器，完整解码后按需重封装或转码为 H.264/yuv420p MP4。图片/播放列表伪装视频、无法解码、输出不完整和转换后超限均失败。最终文件通过 Range API 预览。

## 模型兼容层

两种协议各自构造请求并统一解析为内部 Zod 模式。图片使用 data URL。视频不直接发送原文件：worker 使用 FFmpeg 生成 JPEG 关键帧并保存，再由 Chat Completions 以多图片输入分析，因此不依赖公网媒体地址。

帧数规则为 `min(5, max(1, ceil(durationSeconds)))`，时间点采用每个等分区间的中点。这样短视频约每秒一帧且避开首尾黑场，超过 5 秒的视频固定覆盖 10%、30%、50%、70%、90%。帧最长边缩放至 1280 像素并以质量 0.85 的 JPEG 编码，在覆盖范围和请求体大小之间取得平衡。

本应用使用 FFmpeg 提取视频画面，但不分析音轨。Qwen3.7 仅用于视觉理解，ASR、语言和字幕输出保持在范围外。Responses 不假设非标准多图片视频分析能力。
